# T3.3 — historial SQL de conversación: flujo actual y motivo de la pausa

Este documento cumple el requisito del "Plan técnico inmediato del módulo
RAG — versión 1.3" de documentar el flujo actual **antes** de acotar la
ventana de historial SQL, y deja registrado por qué esa entrega quedó
detenida (decisión del usuario, 2026-08-26) en vez de implementarse.

## 1. Flujo actual, de punta a punta

### 1.1 Persistencia (frontend ↔ SQL)

Cada turno de conversación se persiste en dos llamadas independientes del
frontend a `rag/backend/rag/api/routes/conversations.py`:

- `POST /api/conversations/{id}/messages` con `role="user"` — al enviar la
  pregunta.
- `POST /api/conversations/{id}/messages` con `role="assistant"` — al
  recibir la respuesta completa.

Cada mensaje se guarda como una fila en la tabla `messages`
(`rag/backend/rag/api/models.py::Message`), sin ningún límite de cantidad
por conversación. Esta escritura es **completamente independiente** del
grafo LangGraph: ocurre siempre, tenga o no el servidor un checkpoint en
memoria para esa conversación.

### 1.2 Lectura para continuar una conversación (SQL → RAG)

`rag/backend/rag/api/main.py::_get_initial_messages()` es el único lugar
que lee el historial de `messages` para alimentar al grafo:

```python
state = await graph.aget_state(config)
has_checkpoint = bool((state.values if hasattr(state, "values") else {}).get("messages"))
if has_checkpoint:
    return [HumanMessage(content=question)]          # (a) continuación normal

result = await session.execute(
    select(Message).where(Message.conversation_id == conversation_id).order_by(Message.created_at)
)
msgs = result.scalars().all()                          # (b) rehidratación — SIN LÍMITE
...
return history + [HumanMessage(content=question)]
```

Dos caminos:

- **(a) Continuación normal** — `MemorySaver` (el checkpointer en memoria de
  LangGraph) ya tiene el estado de esa conversación (turno 2+, mismo
  proceso del servidor). No se toca SQL para reconstruir historial; solo se
  añade la pregunta nueva. Este es el camino que se ejecuta en la inmensa
  mayoría de los turnos.
- **(b) Rehidratación** — `MemorySaver` NO tiene estado para esa
  conversación (primer turno tras un reinicio del servidor, o tras que el
  proceso nunca la vio). Aquí se hace un `SELECT` **sin ningún `LIMIT`**:
  carga *todos* los mensajes de la conversación desde el principio de los
  tiempos y los inyecta como `HumanMessage`/`AIMessage` en el estado inicial
  del grafo. Es este `SELECT` sin límite el que T3.3 buscaba acotar.

### 1.3 Qué hace el grafo con `state["messages"]` una vez cargado

Se rastreó exhaustivamente (`grep` sobre todo `backend/rag/`) cada lugar que
lee `state["messages"]` / `state.get("messages")`:

| Lugar | Uso | ¿Necesita el historial completo? |
|---|---|---|
| `agent.py::enrich_query_node` → `_history_for_analysis()` | Construye el contexto de análisis/clasificación de la consulta (enriquecimiento, detección de alcance) | **No** — ya está acotado a `_MAX_ANALYSIS_HISTORY_CHARS = 4000` caracteres, tomando los mensajes más recientes hasta agotar ese presupuesto. |
| `main.py::_extract_answer_from_state` | Busca el último `AIMessage` para devolver la respuesta de este turno | No — solo necesita el mensaje más reciente, que siempre está al final. |
| `main.py::_estimate_context_tokens` | Calcula el campo `context_tokens` de la respuesta (`/api/query`, `/api/query/stream`) | **Sí, en el sentido de que su VALOR depende directamente de cuántos mensajes haya en `state["messages"]`** — ver §2. |
| `main.py::_get_initial_messages` (`has_checkpoint`) | Solo comprueba si la lista está vacía o no | No. |

**Importante:** `generate_node` (la generación final de la respuesta) NO
recibe `state["messages"]` en absoluto — solo recibe `context` (los
fragmentos recuperados) y `question` (la pregunta original + su
reformulación contextual de este turno). El historial completo de la
conversación **nunca llega al LLM de generación**; solo influye,
indirectamente y ya acotado a 4000 caracteres, en la etapa de análisis.

## 2. Por qué se detuvo aquí

Acotar el `SELECT` de la §1.2(b) para que solo traiga, por ejemplo, "los
últimos N mensajes" (acotamiento por cantidad) **no es equivalente** en
general: si los mensajes son cortos, `_history_for_analysis` normalmente
recorrería más de N mensajes hacia atrás antes de agotar su presupuesto de
4000 caracteres, así que un tope por cantidad podría cortar contenido que
hoy sí se usa.

Una alternativa **sí demostrable como equivalente para el análisis**:
acotar el `SELECT` por el mismo presupuesto de caracteres que ya usa
`_history_for_analysis` (cargar desde el mensaje más reciente hacia atrás
hasta acumular ~4000 caracteres, igual que ya hace esa función), en vez de
por cantidad de filas. Eso garantizaría que `_history_for_analysis` viera
exactamente el mismo resultado que hoy, sin importar cuán larga sea la
conversación real.

El problema es el campo `context_tokens` (tabla, fila 3): su valor de hoy
es una función directa de "cuántos mensajes trae `state['messages']`". Si
`state['messages']` se llena con el historial acotado en vez del historial
completo, **el valor reportado de `context_tokens` cambia** — específicamente
para el primer turno de una conversación larga después de un reinicio del
servidor (camino (b) de §1.2). Es un caso específico y poco frecuente, pero
es un cambio real de valor, no solo de fórmula — y T3.7 exige explícitamente
que el significado/valor de `context_tokens` no cambie.

El plan indica expresamente, para esta entrega: *"detener si no se puede
demostrar equivalencia"*. Presentado este hallazgo al usuario (Juan,
2026-08-26), su decisión fue **detener T3.3 por ahora** y continuar con las
entregas que no dependen de ella (T3.5–T3.7, T4). T3.4 ("reducir autoridad
de MemorySaver"), que el plan condiciona explícitamente a que T3.3 esté
resuelta, queda igualmente en pausa.

## 3. Posibles caminos si se retoma T3.3 más adelante

Ninguno de estos se implementó — quedan aquí solo como opciones evaluadas:

1. Acotar el `SELECT` por presupuesto de caracteres (equivalente para
   `_history_for_analysis`) y, en el mismo cambio, resolver `context_tokens`
   de otra fuente (p. ej. contar directamente en SQL cuántos mensajes/tokens
   tiene la conversación completa, en vez de depender de
   `state["messages"]`) para que su valor no dependa del acotamiento.
2. Aceptar y documentar explícitamente que `context_tokens` puede diferir
   en el caso específico de rehidratación tras reinicio — requeriría
   autorización explícita del usuario por tratarse de un cambio de valor en
   un campo público de la API.
3. Separar ambos usos por completo: que `enrich_query_node` obtenga su
   contexto de análisis con una consulta SQL propia y acotada (sin pasar
   por `state["messages"]`), dejando la rehidratación de
   `_get_initial_messages` sin cambios. Esto no "acota la ventana de
   historial SQL" que carga `state["messages"]` (que es lo que pide T3.3
   literalmente), pero sí evita seguir cargando historial innecesario para
   el análisis en conversaciones largas.
